# Project Review — 2026-04-29

## Scope
- Reviewed project structure, Gradle setup, API layering, and key service orchestration flows.
- Performed static verification of dependencies, controllers, exception handling, and traversal query patterns.
- Runtime test execution was not confirmed in this environment due to wrapper download constraints.

## What is good
1. **Clear layered architecture direction**
   - `api`, `application`, `domain`, and `infrastructure` boundaries are present and mostly respected.
2. **Reasonable quality baseline**
   - Spotless, Checkstyle, and PMD are configured in Gradle.
3. **Migration discipline**
   - Flyway is enabled and migration path is versioned.
4. **Service orchestration is centralized**
   - `PersonService` and `RelationshipService` own core orchestration logic.

## Key risks and gaps

### 1) Security pipeline is not enabled in current codebase
- `spring-boot-starter-security` is commented out in Gradle.
- JWT properties exist in config, but there is no active Spring Security filter chain in source.
- **Risk:** API endpoints are likely open at application level unless protected by external infrastructure.

### 2) Invalid enum input can surface as generic 500 errors
- `Gender.valueOf(...)` and `RelationshipType.valueOf(...)` are called directly from request payload strings.
- `GlobalExceptionHandler` does not map `IllegalArgumentException` explicitly, and generic exceptions are returned as 500.
- **Risk:** client input errors can appear as internal server errors instead of consistent 4xx responses.

### 3) N+1 query pattern in relationship traversal responses
- `getParents`, `getChildren`, `getAncestors`, and `getDescendants` repeatedly call `personRepository.findById(...)` inside stream pipelines.
- **Risk:** increased query count and latency on larger family graphs.

### 4) API ownership convention is inconsistent
- Relationship-derived endpoints are split across person and relationship controllers.
- **Risk:** lower API discoverability and higher maintenance cost due to mixed resource ownership conventions.

### 5) Test dependencies and test suite are missing
- Test dependencies are commented out in Gradle.
- No active tests are present under `src/test`.
- **Risk:** low confidence for refactors and regression prevention.

## Prioritized recommendations

### High priority
1. Enable Spring Security dependencies and wire JWT authentication/authorization flow.
2. Add robust enum parsing and explicit exception mapping (`IllegalArgumentException` -> 400 with clear message).
3. Restore test dependencies and add baseline coverage:
   - service unit tests for person/relationship workflows.
   - controller slice tests for validation and status mapping.

### Medium priority
1. Remove N+1 patterns by loading persons in batch (`findAllById`) and mapping in-memory.
2. Standardize API ownership convention (resource-centric or relation-centric) and apply consistently.

### Low priority
1. Define API standards for pagination/sorting/default limits on list endpoints.
2. Extend operational readiness with explicit readiness/liveness conventions and basic alerting.

- This is an execution-environment limitation and should not be interpreted as direct code quality evidence.
