# Project Review (Revised) — 2026-04-29

## Executive Summary
- This review reassesses the backend from four angles: architecture quality, production readiness, technical risk, and scalability.
- The project has a solid structural foundation, but two P0 gaps must be addressed before release: security activation and minimum test baseline.
- Findings in this report are normalized against concrete source-code evidence.

## Current State Snapshot
- Core stack: Spring Boot 3.3.5, Java 21, JPA, Flyway, PostgreSQL, Actuator.
- Quality gates are configured: Spotless, Checkstyle, and PMD.
- Package organization follows a clean direction: Domain/Application/Infrastructure/API.

## Strengths
1. **Clear layering and maintainability**
   - `person`, `relationship`, and `common` modules maintain relatively clean boundaries.
2. **Schema migration discipline**
   - Flyway is used instead of `ddl-auto=create/update`, which is better aligned with production practices.
3. **Centralized exception handling baseline**
   - `GlobalExceptionHandler` provides a single place for REST error orchestration.
4. **Good quality-tooling foundation**
   - Spotless, PMD, and Checkstyle provide a solid base for stable CI pipelines.

## Key Findings (Prioritized by Impact)

### P0 — Security Is Not Effectively Enabled
- `spring-boot-starter-security` is commented out in Gradle.
- Security test dependency is also commented out.
- JWT configuration exists, but no active security filter chain/policy is visible.
- **Impact:** APIs may be unintentionally exposed.

### P0 — Missing Test Dependencies and Baseline Coverage
- `spring-boot-starter-test` and `spring-security-test` are commented out.
- **Impact:** no reliable safety net for refactoring and regression control.

### P1 — Unsafe Enum Validation (Potential 500 Responses)
- `Gender.valueOf(...)` and `RelationshipType.valueOf(...)` throw `IllegalArgumentException` on invalid input.
- `GlobalExceptionHandler` currently catches generic `Exception` and returns 500, so invalid client input can be surfaced as system error.
- **Impact:** unstable API error contract and poor client-side error handling.

### P1 — N+1 Query Pattern in Relationship Traversal APIs
- Parent/child/ancestor/descendant flows repeatedly call `personRepository.findById(...)` per mapped ID.
- **Impact:** significant DB round-trip growth on large genealogy graphs.

### P2 — API Surface Ownership Inconsistency
- Relationship-oriented endpoints are split between `RelationshipController` and `PersonController`.
- **Impact:** lower discoverability and ongoing ownership ambiguity as the API grows.

### P2 — Weak Type Safety in Tree Persistence Repository
- `PersonTreeRepositoryImpl` uses `List<?>` and casts to `PersonTreeEntity`.
- **Impact:** higher runtime `ClassCastException` risk if query result shape changes.

## Technical Recommendation Packages

### Package A (Mandatory Before Release)
1. Re-enable Spring Security dependencies and implement `SecurityFilterChain`.
2. Define explicit endpoint policies (public/authenticated/admin).
3. Re-enable test dependencies and add smoke tests for auth and critical CRUD endpoints.

### Package B (API Contract Stability)
1. Replace raw string-based enum parsing with safer enum binding + custom validation/conversion.
2. Add explicit handlers for `IllegalArgumentException` and `MethodArgumentTypeMismatchException` returning 400 with clear messages.
3. Standardize error schema (business code, field metadata, optional trace ID).

### Package C (Performance and Scalability)
1. Replace per-ID lookup with batch loading (`findAllById`) and in-memory mapping (`Map<Long, Person>`).
2. Define default pagination/limit policy for potentially large list responses.
3. Remove `List<?>` casting in tree repository and use typed query results.
