# Re-review Report (Round 4)

Date: 2026-04-28  
Scope: Coding, `docs/`, `database/`  
Baseline: Follow-up to findings documented in `docs/repo-review-2026-04-28.md` and prior re-review rounds.

## Conclusion

A fresh re-review shows the core previously reported issues have largely been addressed. Relationship type canonicalization, validation coverage, exception strategy, and database/doc alignment are now consistent with the current codebase.

## Status vs Previous Findings

### 1) Relationship type canonicalization (**Resolved**)

- `RelationshipService` now normalizes the incoming relationship type and uses `type.name()` in duplicate checks.
- Repository predicates and SQL partial indexes align on uppercase values (`PARENT_OF`, `SPOUSE_OF`).

**Evidence**
- `src/main/java/com/genealogy/relationship/application/service/RelationshipService.java`
- `src/main/java/com/genealogy/relationship/infrastructure/persistence/repository/JpaRelationshipRepository.java`
- `database/init/init.sql`

### 2) Service abstraction leak in `PersonService` (**Resolved**)

- `PersonService` depends only on `PersonRepository` and uses paginated access through the repository abstraction.

**Evidence**
- `src/main/java/com/genealogy/person/application/service/PersonService.java`
- `src/main/java/com/genealogy/person/domain/repository/PersonRepository.java`

### 3) Raw `RuntimeException` usage in main business flows (**Resolved**)

- Not-found and business-rule paths now use typed exceptions (`ResourceNotFoundException`, `BusinessException`) and are mapped by global exception handling.

**Evidence**
- `src/main/java/com/genealogy/person/application/service/PersonService.java`
- `src/main/java/com/genealogy/relationship/application/service/RelationshipService.java`
- `src/main/java/com/genealogy/common/exception/GlobalExceptionHandler.java`

### 4) Request validation gaps (`@Valid` and DTO constraints) (**Resolved**)

- Controllers now apply `@Valid` for request bodies.
- DTOs define bean validation constraints for required and bounded fields.

**Evidence**
- `src/main/java/com/genealogy/person/api/PersonController.java`
- `src/main/java/com/genealogy/relationship/api/RelationshipController.java`
- `src/main/java/com/genealogy/person/application/dto/CreatePersonRequest.java`
- `src/main/java/com/genealogy/person/application/dto/UpdatePersonRequest.java`
- `src/main/java/com/genealogy/relationship/application/dto/CreateRelationshipRequest.java`

### 5) Empty ERD documentation (**Resolved**)

- `docs/database/erd.md` is now populated with an ERD, relationship notes, and constraints.

**Evidence**
- `docs/database/erd.md`

## Remaining Improvement Opportunities

### A) Standardize enum-input validation messaging (**Open, Low**)

- `gender` and `relationship type` values are parsed with `Enum.valueOf(...)`; invalid values are currently handled by generic exception flow.
- Consider dedicated validation (custom annotation or explicit whitelist) to return more precise client-facing messages for invalid enum values.

**Evidence**
- `src/main/java/com/genealogy/person/application/service/PersonService.java`
- `src/main/java/com/genealogy/relationship/application/service/RelationshipService.java`
- `src/main/java/com/genealogy/common/exception/GlobalExceptionHandler.java`

## Overall Assessment

- **Code quality trend:** Improved.
- **Docs/database consistency:** Improved and largely aligned.
- **Risk level vs previous review:** Reduced from Medium/High to mostly Low.
